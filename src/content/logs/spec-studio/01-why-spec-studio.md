아이디어는 많았다. AI에게 부탁하면 ‘딸깍’ 한 번으로 돌아가는 화면까지 만들어 볼 수 있었다. 어려운 건 그렇게 만든 프로젝트를 이어가는 일이었다. 처음에는 화면부터 띄우면 됐다. 계속 만들기로 한 뒤에는 무엇을 검토하고 어디에 기록할지 다시 정해야 했다. 기획 때 본 시안과 실제 구현이 다르면 다음 작업에서 어느 쪽을 기준으로 삼을지도 애매했다.

만드는 속도가 빨라졌다면 작업 방식부터 정해 두고 시작해도 괜찮겠다고 생각했다. 처음에 시간을 써 두면 품질을 챙기면서도 다음 작업을 이어가는 데 시간을 덜 들일 수 있지 않을까. 우선 정하고 싶었던 건 변경이 생길 때 무엇을 보고 결정하고, 구현이 끝나면 무엇을 남길지였다. 명세를 코드와 같은 저장소에 두는 방식은 [OpenSpec](https://github.com/Fission-AI/OpenSpec)을 참고했다.

AI가 내 요청을 기획서로 정리해 주면 어떤 동작을 만들려는지 글로 읽을 수 있다. 가령 ‘입력이 잘못되면 오류를 표시한다’고 써도, 오류를 어디에 보여줄지와 이미 쓴 내용을 남겨둘지는 화면을 직접 눌러 볼 때 판단하기 쉽다. 그래서 화면이 바뀌는 일에는 기획 단계부터 Storybook에서 열고 조작할 수 있는 시안을 붙이기로 했다.

그러고 나니 시안도 어떻게 만들지 정해야 했다. 시안과 제품에서 폼을 따로 만들면 처음에 같아 보여도 고칠 때 서로 달라질 수 있다. 버튼과 입력창 같은 기본 요소는 디자인 시스템에 두고, 여러 화면에서 반복되는 폼과 페이지 배치도 [공용 코드로 만들기로 했다](/blog/projects/spec-studio/logs/02-shared-ui-for-storybook/). Storybook은 그 코드를 가져와 가상 데이터로 보여준다. 제품은 같은 코드에 실제 데이터와 동작을 연결한다.

기획서와 시안, 요구사항, 구현과 검증 기록은 한 변경 건으로 묶었다. 사람은 텍스트와 화면을 함께 보고 요구사항을 검토한다. 구현 뒤에는 어느 코드에서 완료 기준을 확인했는지 QA 결과와 함께 기록한다. 승인한 동작이 달라지면 요구사항을 다시 검토한다. 사람이 QA 결과를 수용하면 확인한 동작을 현행 명세로 확정한다. 기획 시안은 당시 무엇을 제안했는지 보여주는 기록으로 보관한다. 다음 변경을 계획할 때는 현행 명세를 본다.

이 흐름을 쓰려고 Spec Studio를 만들었다. 첫 적용 대상도 Spec Studio였다. 처음부터 체계를 마련하는 편이 좋은 제품을 더 빨리 만드는지는 아직 모른다. 다음 변경을 열었을 때 지난번에 무엇을 만들기로 했고 어디까지 확인했는지, 남겨 둔 기록으로 알 수 있는지부터 보려 한다.
