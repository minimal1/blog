앞 작업이 끝나야 시작할 수 있는 작업 두 개를 생각해 보자. 메인 에이전트가 첫 작업을 다른 에이전트에 맡기고 ‘끝났습니다’라는 답을 받았다. 이 답만으로는 그 세션이 승인된 작업을 맡았는지, 실제로 어떤 코드에서 검증을 실행했는지 알기 어렵다. 두 번째 작업을 시작할 시점을 대화 속 완료 보고에 맡기면, 새 세션에서 그 근거를 찾기도 어렵다.

그래서 처음에는 작업을 하나씩 위임하기로 했다. 사용자가 실행을 요청하고 계획이 승인된 상태에서, 메인 에이전트가 선행 작업이 끝난 항목 하나를 확보한다. Aru에서 실제로 응답한 담당 세션을 그 작업에 연결한 뒤 지시를 전달한다. 어느 프로젝트의 어떤 계획과 작업을 누구에게 맡겼는지, 위임 시도마다 구분해서 남긴다.

담당 에이전트는 자기 세션으로 작업을 시작하고 검증을 실행한다. 메인 에이전트가 통과한 검증 실행을 확인하면 같은 담당 세션이 완료를 기록한다. 메인 에이전트는 기록에서 완료와 점유 해제를 확인한 후 다음 작업을 맡긴다. 검증이 실패하거나 취소되면 그 작업은 보류된다. 다시 시작할 때도 보류 전의 검증 결과를 그대로 가져다 완료할 수 없다.

격리된 테스트 프로젝트에서 실제 Aru 서브 에이전트 둘로 확인했다. 첫 작업이 진행 중일 때 두 번째 위임을 확보하려는 요청은 거절됐다. 첫 작업이 끝나 담당 세션의 점유가 풀린 뒤 두 번째 작업을 배정했다. 두 작업 모두 담당 세션과 통과한 검증 실행 ID가 기록에 남았다. 테스트에서 쓴 승인 입력은 실험을 위해 만든 것이다. 실제 제품의 계획 승인과 QA 수용은 [사람이 결정한다](/blog/projects/spec-studio/logs/01-why-spec-studio/).

이번에 확인한 범위는 한 번에 한 작업을 넘기는 흐름이다. 여러 에이전트가 같은 저장소를 동시에 수정할 때의 충돌이나, 오래 걸리는 작업의 자동 재시도는 다루지 않았다. 먼저 남긴 것은 두 번째 작업을 시작해도 된다고 판단한 근거다.
