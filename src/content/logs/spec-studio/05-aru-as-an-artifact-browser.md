처음에는 Aru 안에서 Spec Studio 프로젝트를 열고, 작업 환경을 준비하고, 변경 건을 검토하고, 작업 채팅까지 열 수 있게 하려 했다. 프로젝트 등록부터 구현을 요청하는 순간까지 한 화면에서 이어지면 편할 것 같았다. 그러려면 선택한 디렉터리와 Aru 프로젝트가 맞는지, 열려는 채팅이 그 프로젝트의 것인지, 채팅을 다시 열 때 어떤 세션을 재사용할지까지 화면에서 다뤄야 했다.

실제 Aru에서 연결을 확인한 뒤에도 작업 환경을 준비하는 채팅 요청은 두 번 취소됐다. 테스트 환경에서는 확인했던 초안과 세션 재열기를 실제 Aru에서는 검증하지 못했다. 어디까지 한 화면에서 할지 다시 생각했다. 당장 Aru 화면에서 필요했던 건 프로젝트를 열고 앞서 정한 기획과 작업, 현행 명세를 찾아 읽는 일이었다.

그래서 플러그인의 첫 화면을 IDE의 파일 탐색기처럼 바꿨다. 왼쪽 트리의 맨 위에는 프로젝트를 놓았다. 펼치면 변경 건, 기획, 작업, 현행 명세가 나오고, 그 아래에서 결과물 하나를 고르면 오른쪽에서 읽을 수 있다. 초기화, 승인과 작업 실행은 명령줄 도구에 남겼다. Storybook 시안은 기획 자료에서 참조하고 별도 Storybook에서 연다.

새 플러그인을 실제 Aru에 설치해 트리에서 프로젝트와 변경 자료를 열어 봤다. 새 패키지에 제품 상태를 바꾸는 실행 모듈이 빠졌는지도 확인했다. 채팅을 여는 기능은 범위에서 빠졌고, 앞서 실패한 검증은 당시 기록에 남겼다.

[기획과 실제 구현을 연결하는 방식](/blog/projects/spec-studio/logs/01-why-spec-studio/)은 그대로 쓸 수 있었다. 화면을 줄이고 나니 다음에 개선할 일도 구체적이었다. 프로젝트에 변경 자료가 쌓일수록 원하는 문서 하나를 찾아 여는 시간이 얼마나 드는지 확인해야 했다.
