기획 시안을 제품과 같은 UI로 만들기로 했는데, 막상 그 UI를 처음 만들 때 어디서 시작할지가 애매했다. 당시 저장소에는 브라우저에서 열 수 있는 React 샘플과 별도로 만든 Aru 플러그인 화면이 있었다. 각각 동작했지만 샘플에서 본 입력창을 제품에서 그대로 쓸 수는 없었다. Storybook과 제품이 함께 가져다 쓸 원본부터 필요했다.

그래서 디자인 시스템 자체를 첫 시안의 대상으로 삼았다. 버튼과 입력창, 대화상자의 후보를 공용 패키지에 만들고 Storybook에서 불러왔다. 이 단계에서 코드가 있다는 건 검토할 화면이 생겼다는 뜻이었다. 어떤 동작을 공용으로 가져갈지는 화면을 본 뒤에 정했다.

대화상자로 보면 차이가 잘 드러난다. 열렸을 때 키보드 초점이 안으로 들어오는지, 닫으면 열었던 버튼으로 돌아오는지는 그림만 보고 알 수 없다. 공용 컴포넌트를 Storybook에서 띄우니 긴 본문을 좁은 화면에서 스크롤하거나, 겹쳐 열린 대화상자를 Escape로 닫아 볼 수 있었다. 코어를 확정할 때는 같은 공용 코드로 Storybook을 다시 빌드해 이 동작들을 확인했다. 이때 검증한 대상은 디자인 시스템이었다. 설치된 플러그인의 전체 동작은 이후에 따로 검증했다.

디자인 시스템을 확정한 뒤에는 공용 요소를 조합한 작업 화면도 같은 방식으로 만들었다. Storybook은 가상 프로젝트와 변경 건을 넣어 등록, 요구사항 검토, 오류 같은 상태를 재현했다. Aru 플러그인은 같은 화면 코드에 실제 프로젝트 데이터와 동작을 연결했다. 등록 화면의 배치나 오류가 표시되는 위치도 한곳에서 바꿀 수 있게 됐다.

React와 shadcn/ui는 Spec Studio를 만들면서 고른 도구다. 제품마다 기술 선택은 달라도 **그 제품이 쓰는 UI 코드를 시안에서도 재사용한다**는 원칙은 같다. [처음 작업 방식을 정할 때](/blog/projects/spec-studio/logs/01-why-spec-studio/) 걱정했던 시안과 구현의 차이 중에서, 같은 화면을 두 번 만들면서 생기는 부분부터 줄여 보기로 했다.
